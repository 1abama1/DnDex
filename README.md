# DnDex — The Adventurer’s Codex

DnDex — двуязычная платформа для поиска и организации настольных ролевых приключений. Каталог, заявки, кабинет мастера и игрока, отзывы и профили работают с настоящим Supabase. Стек сохранён: React 19, строгий TypeScript, Vite 8, Tailwind CSS 4, React Router 7, TanStack Query, React Hook Form и Zod.

## Запуск

Для всех инструментов разработки используйте Node.js **22.22.2+ в ветке 22**, **24.15+ в ветке 24** или **26+**, npm и Supabase с PostgreSQL 15+.

```sh
npm ci
```

Скопируйте `.env.example` в `.env.local` и заполните:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-public-anon-or-publishable-key
```

В браузер передаётся только публичный anon/publishable key. Service-role key здесь использовать нельзя. Переменные `VITE_*` включаются в сборку, поэтому после их изменения перезапустите dev-сервер или пересоберите приложение.

```sh
npm run dev
npm run build
npm run preview
```

Без корректных переменных приложение показывает главную и понятное состояние «сервис не подключён». Данных, авторизации и сохранения в этом состоянии нет. **Деморежима и автоматического перехода на моковые данные нет**. Ошибки настроенного backend отображаются как ошибки.

## Supabase и обновление базы

### Новый проект

Выполните весь `src/sql/schema.sql` в Supabase SQL Editor. Он включает базовую схему и актуальную миграцию безопасности. Не выполняйте только верхнюю часть файла.

### Существующий проект

Сначала проверьте изменения на staging и сделайте резервную копию обычным процессом команды. **Перед выпуском frontend** выполните `src/sql/migrations/202611170001_integrity_and_privacy.sql` через SQL Editor или существующий процесс миграций. Приложение не запускает SQL самостоятельно. Старую схему поверх действующего проекта повторно запускать не нужно.

Миграция:

- Сохраняет существующие записи. Новые ограничения текста добавлены как `NOT VALID`: старые строки не удаляются; при их последующем изменении нужно исправить невалидное содержимое.
- Ограничивает чтение `campaigns.discord_url` на уровне колонок. Публичное представление оставляет совместимую колонку с `NULL`; реальное приглашение выдаёт только RPC `get_campaign_discord(target_campaign)` мастеру или принятому игроку.
- Сохраняет публичный список принятых игроков; заявки `pending`/`rejected` видны только их автору и мастеру.
- Разрешает новые заявки только от имени текущего пользователя, со статусом `pending`, в открытую кампанию со свободными местами. Мастер не может вступить в свою кампанию.
- Сериализует принятие заявок блокировкой родительской кампании. Решение можно изменить только с `pending` на `accepted`/`rejected`; размер группы нельзя уменьшить ниже числа принятых игроков.
- Разрешает создание отзывов только принятым игрокам, кроме мастера. Существующие авторы сохраняют право редактировать и удалять свои отзывы. Идентификаторы автора и кампании отзыва неизменяемы.
- Добавляет `available_seats` в публичное представление для фильтрации по свободным местам. Завершённую или отменённую кампанию нужно сначала открыть заново, прежде чем переводить в процесс.

Права на приватную колонку намеренно означают, что старые клиенты с `campaigns.select('*')` потребуется обновить. Сервисный слой использует явные проекции публичных полей. Не возвращайте общий `GRANT SELECT ON campaigns`, чтобы исправить старый клиент: это раскроет приглашения.

В Supabase включите публикацию Realtime для `campaigns`, `campaign_activity`, `reviews` (Database → Publications/Replication). Миграция заменяет `participants` на `campaign_activity` в стандартной публикации `supabase_realtime`, если она существует. **Не включайте `participants` обратно:** DELETE-события Realtime могут раскрывать составной ключ заявки без проверки RLS. Сигнал `campaign_activity` содержит только ID публичной кампании и номер изменения; строки заявок загружаются обычным запросом с RLS. Настройте Site URL и Redirect URLs в Auth под свой домен и localhost; включите нужный режим подтверждения email и почтовую доставку. При подтверждении email регистрация показывает просьбу проверить почту. Обложки/аватары используют HTTPS URL; загрузка файлов и Storage bucket не требуются.

SQL и политика доступа опираются на [RLS и security-invoker views](https://supabase.com/docs/guides/database/postgres/row-level-security), [права колонок](https://supabase.com/docs/guides/database/postgres/column-level-security) и [правила Realtime](https://supabase.com/docs/guides/realtime/postgres-changes). Проверяйте права и JWT реальными пользователями на staging перед продакшеном.

## Архитектура

```text
src/
  components/
    auth/             # вход и регистрация
    campaigns/        # карточки, каталог, обложки, досье, участие, редактор, отзывы
    layout/           # шапка, навигация, защита маршрутов
    profile/          # форма профиля
    ui/               # общие контролы, диалоги, обратная связь, Markdown
  hooks/              # интеграция Query, auth, debounce, единственная Realtime-подписка
  lib/
    domain.ts         # Zod-схемы, фильтры URL, статусы и правила показа действий
    queryKeys.ts      # иерархические ключи кеша
    cache.ts          # обновления кеша после мутаций
    errors.ts         # безопасные локализованные ошибки
  services/           # доступ к Supabase и валидация внешних ответов
  pages/              # страницы, тяжёлые маршруты загружаются лениво
  sql/                # полная схема, версия миграции и PostgreSQL-тесты
  translations.ts     # русский и английский
```

Компоненты не собирают запросы БД. Сервисы валидируют ответы Zod; хуки управляют серверным состоянием и мутациями. При смене аккаунта кеш очищается, чтобы персональные данные не переходили другому пользователю. В callback Auth нет запросов Supabase; загрузка профиля выполняется отдельным Query.

Каталог загружает по 12 кампаний, возвращает точное количество и использует устойчивую сортировку. Поиск отправляется после 300 мс тишины, устаревшие запросы отменяются. Фильтры хранятся в URL (`q`, `type`, `system`, `status`, `sort`, `seats`, `page`). Ввод поиска заменяет текущую запись истории; выбор фильтров добавляет запись. Назад/вперёд восстанавливает URL и интерфейс.

На уровне Layout работает один Realtime-канал с тремя обработчиками таблиц. События объединяются за 150 мс, обновляются активные запросы. Для DELETE без `campaign_id` обновляется затронутое семейство кеша. При размонтировании/смене аккаунта канал и таймер удаляются.

## Дизайн и доступность

Токены Tailwind v4 и общие стили находятся в `src/index.css`. Основные поверхности: `bg-primary`, `bg-secondary`, `bg-card`; текст: `text-primary`, `text-secondary`, `text-muted`; золото — основные действия, фиолетовый — тип кампании, зелёный — доступность и успех, красный — опасность. Типографика: Cormorant Garamond для крупных заголовков и Inter для интерфейса, с системными fallback. Google Fonts необязателен для работы интерфейса; для полностью автономного развёртывания шрифты можно разместить локально.

Оригинальные SVG-пейзажи входят в код, различаются по игровой системе и не требуют сторонних изображений. Некорректная или недоступная обложка/аватар заменяется устойчивой заглушкой. Отсутствие рейтинга не выдаётся за высокую оценку. Статистика кабинета вычисляется из данных пользователя.

Диалоги используют нативный `<dialog>`: модальность, удержание фокуса, Escape, возврат фокуса и блокировка прокрутки. У полей уникальные ID, доступные подписи и связанные сообщения ошибок. Вкладки поддерживают стрелки/Home/End; рейтинг — radio controls. Добавлены skip-link, видимый focus, сообщения `status`/`alert`, семантические ссылки и reduced-motion. Формы предупреждают о несохранённых изменениях при переходе и закрытии вкладки; черновики в localStorage не сохраняются. Markdown не включает raw HTML, внешние изображения из Markdown не загружаются.

Адаптация предусмотрена для 320/375/768/1024/1440 px и больших экранов: мобильная навигация, раскрываемые фильтры, сетки 1/2/3 колонки и перенос панели участия над описанием.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run build
npm run format:check
npm audit
```

`npm run test:watch` запускает Vitest в режиме наблюдения. React Testing Library проверяет общие контролы, состояния участия, debounce, кеш и Realtime. Сервисы тестируются на границе Supabase. SQL-тесты запускают настоящий локальный PostgreSQL-движок PGlite, создают тестовые auth-роли и проверяют миграцию, RLS, приватные поля, ограничения заявок, вместимость и отзывы. Они не подключаются к рабочему Supabase. PGlite не проверяет работу PostgREST, почты, hosted Realtime или истинную конкуренцию независимых подключений.

Статус выполненных проверок и ограничения проверки приведены в `docs/MODERNIZATION.md`. Lighthouse-цели не выдаются за измеренные результаты.

## Развёртывание

После применения миграции задайте публичные переменные окружения в хостинге, выполните `npm ci` и `npm run build`, опубликуйте `dist/`. Для SPA нужен fallback всех маршрутов на `index.html`; `vercel.json` уже содержит rewrite. Проверьте вход, подтверждение email, создание/редактирование, принятие последнего места из двух сессий, отзывы и Realtime на staging. Автоматической публикации и изменения удалённой базы в этой доработке нет.
